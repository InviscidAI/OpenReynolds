# What is in here

Small scripts and some notes, refreshed from the distribution at the start of every
session. They are offered, not imposed: use them, edit them, replace them, or ignore
them. Nothing checks whether you did.

Each takes `--help`.

| | |
|---|---|
| `geometry_view.py` | Surfaces (`.stl`, `.obj`, `.ply`, `.vtk`, and `.step`/`.iges` tessellated coarsely for the picture and thrown away afterwards) drawn from four fixed views with every facet edge and the bounding-box ticks on, plus open edges, non-manifold edges, connected bodies, extents and face-area range. No verdicts: whether 40 open edges matter depends on where they are. |
| `cad_convert.py` | STEP and IGES to STL. gmsh here is built against OpenCASCADE, so a `.step` is read as B-rep -- exact circles, declared units, real trimmed surfaces -- and `import gmsh` will answer questions about it directly, which is the intended way to decide the tessellation. This script decides nothing: you pass `--clmax` and it converts, then reports the unit it read or was given, the entity counts, the tightest curve it found and the sagitta that implies, the facet count and longest edge that came out, and the gmsh calls in order. It refuses twice, both times where a wrong answer looks right: no `--clmax`, and a file that declares no unit with no `--unit`. |
| `mesh_look.py` | A mesh looked at and measured in one call, straight from `constant/polyMesh` -- no solve, no fields, no time directory. One PNG: the boundary with **one colour per patch** (2D gets the patches and the cells; 3D gets the patches and a cut on each axis), and under it the table -- cells, faces, points, the bounding box, whether it is one cell thick, and for every patch its type, face count, area, centre and mean unit normal, which is what tells an inlet from an outlet without guessing from where it sits. The cell zones and face zones in `constant/polyMesh` are listed under the patches -- name and count either format, and a cell zone's centroid and the box its cell centres span where the file is ascii -- because a sliding interface, a frozen rotor and an overset region are all named against a zone, and a dictionary naming a zone the mesh does not have fails at the first solver step. A mesh with no zone files says so rather than saying nothing. `checkMesh` runs with it and its verdict and the three metrics a solver minds are in the same report. `--json` writes the same facts for a script to read. `--out` and `--json` are relative to where you run it from, like every other script here (not to the case); without `--out` the picture is `<case>/look.png`, and the report's `picture:` line is the absolute path written. |
| `disk.py` | What is filling the workspace, and what of it is safe to delete. There is one disk: an account is capped at one instance, a new study joins the existing one, and every study ever run is a sibling directory under `/work` sharing a single 20 GB quota. So a 24 MB case can be refused because an animation run three weeks ago left 3 GB of frames next door -- measured 2026-09-08 at 30.8 GB used, of which 24.5 GB was regenerable scratch nothing was responsible for clearing. `report` ranks every directory by size and says how much of each could be produced again. `prune` removes only that -- `processor*`, solution times other than the latest, `VTK/`, animation frames -- and never `0/`, `constant/`, `system/`, `log.*`, `postProcessing/`, figures, reports or `Allrun`/`Allmesh`/`build.py`, and never the `polyMesh` inside a time directory, which on a moving mesh is the only record the run keeps of its own motion -- on such a time the fields beside that mesh are still offered one by one, because keeping the whole directory freed nothing at all on the moving-mesh case that most needs the space. It is a dry run unless `--apply`, it refuses to guess which study to prune, and it never deletes a whole study: removing one is a person's decision and this exists to make that unnecessary. |
| `mesh_digest.py` | `checkMesh` output as a metric table — the numbers and the patch table, no thresholds applied. |
| `cells_estimate.py` | Cell count predicted from the STL and the snappy dictionaries, before the build rather than after it. |
| `log_digest.py` | Solver log to a residual plot, a last-iteration table, and the continuity and bounding summary. Its first lines say how the run ended and what the residuals were doing when it did -- levelled off (a plateau; under a steady solver on an unsteady flow, the flow being reported), still falling, or climbing (a divergence) -- in words that depend on which, because only the last is a failure. |
| `reattach.py` | Where the flow leaves a wall and where it comes back, off the wall shear: the sign changes along a patch, with the primary reattachment picked out of them as the downstream end of the longest reversed-flow run -- not the first sign change, which on a backward-facing step is the corner eddy, and not the last, which is a secondary bubble. That rule is stated in the report wherever it actually chose between two bubbles, because on a geometry whose downstream separation is the longer one it names that instead. Both of those are printed beside the answer, so a number computed another way can be checked against the same list rather than merely disagreed with. Which sign of tau means attached is measured off `U` (tau tracks the near-wall velocity along a wall; the domain mean says which way downstream is), so no convention has to be known or got right. It reports the local face spacing with the number and rounds the answer to it. It never asserts a length unit it cannot read: with a `--height` other than 1 the answer is in step heights and says `h`; without one -- and `--height 1` is without one, since 1.0 is the flag's default and nothing here can tell an explicit 1 from an unused flag -- it is in whatever the wall's coordinate was and the label is left empty; `--units h` says it by hand, which is also the only way to label a table already sampled in x/h. A label invented here is a comparison switched off in `claims.py`. `--from-file` runs a sampled `.raw` or any two-column table through the same arithmetic; `--plot` draws the curve and the figure carries the number it was drawn from. |
| `claims.py` | The number a figure was drawn from, stamped into the PNG itself, so the picture and the prose can be put side by side. `attach` stamps a figure -- including one a hand-written script drew -- `read` prints what one carries, and `check` reports two claims about the same quantity that disagree, and any claim the written answer contradicts or never quotes. It exists because a study delivered a figure annotated 7.57 with an answer that said 6.4 and reconciled neither; the caption drawn on a figure and the value stamped into it come from one call, so those two at least cannot drift. It exits non-zero on a disagreement -- as `preflight.py` does on a failing finding, and unlike the scripts here that only ever report -- because what it reports is arithmetic rather than judgement. Two claims whose unit labels differ are not compared, since guessing a conversion is how a reconciliation tool starts inventing its own errors, and they are printed as not compared rather than skipped: the all-clear is never shown over a pair nothing checked. |
| `render.py` | Fixed pyvista scenes for a case: mesh cuts and field slices, as PNGs, with cameras that do not move between runs so two of them are a visual diff. `--fields` takes solver outputs and also `vorticity` (signed, out-of-plane) and `Q`, which it computes from `U` rather than leaving to a hand-written script. `--contours N` draws N iso-contour lines over a slice, at levels taken from the field's own range with the two ends left off -- a level sitting exactly on the minimum is a single point and draws nothing, so asking for 10 lines used to be a way to get 8. `--diff OTHER` cashes the fixed camera in: one field of two runs as two panels on **one** colour scale and one camera, plus their difference on a diverging map centred on zero, with those numbers written beside the PNGs in a JSON sidecar rather than only claimed -- two panels each scaled to their own range are not a comparison. The second run is cut on the *first* one's plane; two meshes of the same domain are differenced by resampling one onto the other, and two runs whose bounds are more than 1% of the extent apart, or where the resampling covers under 99.9% of the cut, are refused by name instead of drawn, a difference between two different domains being a plausible picture of nothing. |
| `case_gen.py` | The case files for a mesh that already exists: `0/`, `system/` and `constant/`, sized to the mesh in front of it. It reads the patch names and types out of `constant/polyMesh/boundary`, the cell count, bounding box and smallest cell out of `checkMesh`, and each patch's area, centre and normal out of `mesh_look.py` -- and from those works out which way the inlet flows (its own normal, pointed at the middle of the domain, which is why a U-duct with both ends on the left comes out right), the hydraulic diameter the Reynolds number is on, and whether this is a body in open flow or a passage (a wall patch that is not part of the domain's own bounding box is a body), which sets the free-stream turbulence. Every patch gets a role -- inlet, outlet, wall, slip, symmetry, a belt that moves with the stream, a wheel that spins, empty -- from what you name, then from the mesh's own constraint types, then from the name; and a `boundaryField` entry in every field the turbulence model reads. Give it `--reynolds` and it solves for the viscosity and says so. It builds no geometry: that is the `cad` tool's job. |
| `compressible.py` | The same job for a compressible run: `0/`, `system/` and `constant/` for a transonic or supersonic case on a mesh that already exists. `p` is absolute static pressure in pascals and `T` is a field, which is the whole difference -- an incompressible `p` is p/rho in m2/s2 and a force taken off a compressible one as if it were kinematic is out by rho in both directions. `constant/thermophysicalProperties` takes the place of `transportProperties`: `hePsiThermo`, `perfectGas`, Sutherland transport and one specie's numbers, each printed with its source, and the molar mass and Cp are read back out of the file to give the gamma, the speed of sound, the Mach number, the density, the viscosity and the stagnation conditions it reports -- so there is no nu anywhere and the Reynolds number is an output. The boundary conditions come from the Mach number and the choice is stated: a subsonic outlet gets `waveTransmissive` rather than a `fixedValue` that reflects an arriving shock, a supersonic one gets nothing imposed at all, and `transonic yes` in `fvSolution` follows the same number. `forceCoeffs` is written with `rho rho` and the density field, which is the branch `preflight.py` already judges a compressible case by, and `Aref` on a 3D case is asked for rather than guessed. It reuses `case_gen.py`'s mesh reading and patch roles rather than repeating them, says which of `rhoSimpleFoam`, `rhoCentralFoam` and HiSA is actually on this machine instead of assuming, and for HiSA writes everything except the two scheme files -- those are HiSA's own and the authority for them is the ONERA M6 case in the image, so it prints the `cp` commands and what the files carry rather than inventing a dictionary that parses. |
| `preflight.py` | The cheap questions asked before an expensive run -- patch names against the fields, `empty` treatment on a 2D case, STL scale, Re against nu, predicted cells, checkMesh, a one-iteration probe, Courant and disk -- each answered as a finding with what was measured, what it means, and a repair you may or may not want. |
| `ladder.py` | A ladder of reduced cases for this case, read out of the case itself: the class it appears to be and the evidence for that reading, then the rungs in order -- what each one adds, what to measure on it, the answer that is already known and where it comes from, what counts as passing, and what it costs. The rule is that a rung's answer never comes from another solve: Archimedes, the ITTC-57 line, Kelvin's 19.47 degrees, Hagen-Poiseuille, the divergence theorem. `--rung n` prints one in full with the dictionary edits that would build it. `--record n --status pass\|fail\|skipped --value X` writes a rung's outcome to the study manifest on the volume, where the report's evidence column and `progress_report.py` read it back -- in this session or the next. It edits no case and runs nothing, the exit code is always 0, and climbing none of the rungs is a legitimate choice. |
| `grid.py` | The same quantity on two or more meshes, as a number with an error bar: the refinement ratio of each pair, the order of convergence the solver actually achieved, the Richardson-extrapolated value, Roache's Grid Convergence Index on the fine grid, and the band that falls out of it -- `Cd = 0.412 +/- 0.004` from discretisation, where the only error bar anywhere else in here is `reattach.py`'s half a face spacing. The arithmetic is checked in this repository against NASA Glenn's published worked example (p = 1.786170, 0.97130, GCI 0.103083%), because the four lines of Richardson extrapolation are easy to write and easy to write wrongly, and the ways they mislead are silent. Four of them are handled rather than presumed away: two different refinement ratios, which the textbook single-`r` formula turns into a 20% error in the exponent everything else hangs off, so `p` is solved for out of Celik's relation by bisection (scipy is not on the image) and the equal-ratio case is then the same path rather than a special one; oscillatory convergence, where the middle value is not between the other two and the extrapolation would be arithmetic on a premise the data has already contradicted, reported as oscillatory with the interval the ladder does support and no GCI percentage at all; two grids agreeing to the last digit, which is mesh independence reached and not an order of convergence, so nothing is divided by the difference that is not there; and an observed `p` of -2.3 or 8, printed because it is the most diagnostic thing the triplet has to say and then not used, with the GCI falling back to the scheme's formal order and the clamp named in the output. The safety factor sits beside the band -- 1.25 over three grids with an observed `p`, 3.0 over two with an assumed one, and the report says which is the default -- since a band whose factor is unstated is a band of unstated size. Cell counts become a representative spacing through `N**(-1/3)` or `N**(-1/2)` from `--dim`, or from the mesh's own `empty` patches with that route named, because a plane case here is a one-cell-thick 3D mesh and its cell count cannot say which it is. The counts come from `checkMesh` through `mesh_digest.py` and the quantities from `postProcessing/*.dat` through `results.py`, a restarted series stitched back into one history, and every number in the report is printed beside the case, the file and the column it came from, a ladder being the one place where the wrong column on one of three cases gives a plausible answer. `--json` writes the same facts, and `--png` draws value against `h` with the extrapolation as the asymptote it is. |
| `locate.py` | Where a diverging run went wrong, measured off the case rather than argued: the last written fields with min, max, mean and the extremum's cell, coordinates, owning patch and distance to the domain boundary, ascii or binary mesh alike; the solver log read for the field whose residual or bounding warning degrades first and when, with the Courant tail; and `--compare <other-case>` running the same scan on a second mesh of the same problem, because a value that does not move when the mesh changes is set by the boundary specification, not the grid. It reports in preflight's measured/means/repair register, offers no mechanism -- location over explanation is its whole idea -- edits nothing, and exits 0 whatever it finds. |
| `hisa_env.py` | Where HiSA -- the implicit density-based shock-capturing solver -- is on this instance: baked into the image (newer images, no exports needed), built onto the volume (older images), or absent. Says present, absent, or present-with-unresolved-libraries; for a volume build prints the four export lines a shell needs and the `-x` forwarding `mpirun` needs; prints the path to the ONERA M6 case HiSA ships, which is the shortest route to a correct dictionary set. `--json` for reading it from another script. |
| `layer_report.py` | How much of a wall actually carries a prism layer, measured off the mesh rather than taken from the mesher: the first-cell height at every patch face, `2 \|C_face - C_owner\|`, computed from `points`, `faces` and `owner` so nothing has to have been written and no solver has to have run. Coverage is that height against a reference wall spacing -- the same wall meshed with no layer request (`--ref`), or a spacing you already know (`--wall-spacing`); with neither, the threshold comes from the mesh itself and says so. It exists because snappyHexMesh reports a layer table, cfMesh reports nothing comparable, and the three claims about one hull could not be put next to each other until the meshes were measured with one metric. `--json` for reading it from another script. |
| `wall.py` | The y+ a run actually reached, read back off what it wrote, as against the y+ it was predicted to get. `case_gen.py` prints an a priori estimate from a flat-plate correlation before the solver starts -- on a generated aerofoil O-grid that estimate was y+ ~1200 under a wall function valid to 300 -- and `layer_report.py` measures the first-cell height, which is geometry and carries no velocity. This is the velocity field's own answer, per patch: min, max, mean, and the fractions of the wall sitting in the viscous sublayer, the buffer layer and the log layer, rather than one number for a wall that is never in one region. Three sources, each labelled, whichever the run left behind: `postProcessing/yPlus/<time>/yPlus.dat` from OpenFOAM's own y+ function object (histories stitched across time directories and `_<time>` restart suffixes the way `results.py` does, and the header read by its reader rather than the columns assumed); a written `yPlus` field, whose `boundaryField` carries one value per face so the fractions are real fractions; and `wallShearStress`, from which y+ is derived as `sqrt(|tau|) y / nu` with y the first-cell centre out of `layer_report.py` and nu off `constant/transportProperties` -- refused by name, never defaulted, since a y+ off a guessed viscosity looks measured and is not. It also says which `nut` condition the case ran with against the band that form is written for: every model `case_gen.py` writes gets `nutUSpaldingWallFunction`, which blends through all three regions, so there the finding is informational, and it is sharper on a plain high-Re form measured outside 30-300. Findings in preflight's measured/means register, `--json`, and `--png` for a per-patch y+ range plot. It states the measurement and no instruction; it edits nothing and exits 0 whatever it finds. |
| `heat.py` | The heat a run moved, read back off what it wrote. Per patch: the heat rate in watts, the **area-weighted** mean flux, and the range -- from the `wallHeatFlux` function object's own `postProcessing` table where the run asked for one (its header read by `results.py`'s reader, its rows by the same two-step `wall.py` needed for `yPlus.dat`, a patch name per row being what stops `parse_dat`), and from a written `wallHeatFlux` field integrated against the face areas out of `constant/polyMesh` where it did not -- the plain mean of a graded wall's face values weights a 1 mm2 face like a 1 m2 one. The sign is OpenFOAM's and is reported as written, a flipped one turning a cooler into a heater. **Nu = h L / k** with `h = q / (T_wall - T_ref)`, every one of q, T_wall, T_ref, L and k read from the case or given outright and a missing one refused by the flag that would supply it (`grade.py`'s rule), k coming either from a `kappa` entry or from `rho * Cp * nu / Pr` spelled out in the report. Which **reference temperature** was used is printed beside every number, because the same wall gives three Nusselt numbers against a free-stream, an inlet and a mixed-mean reference: `bulk` is the flux-weighted mixed mean an internal flow's Nu is defined on and the default over a named patch, formed as `sum(phi T) / sum(phi)` with `probe.py`'s weighting; in a duct the fluid at the wall is the hot fluid, so the area average sits above it and a Nu taken on that comes out low. With `--reynolds` and `--prandtl` the measured number is put beside the published one `ladder.py`'s conjugate catalogue names -- the Graetz 3.66 below Re 2300, Dittus-Boelter above it with n from whether the wall is heating or cooling -- each against the accuracy it states for itself (2% and 25%) rather than a tolerance invented here. **Hot spots** are places and not maxima: the peak's cell, coordinates, owning or nearest patch and distance to the boundary through `locate.py`'s readers, plus how large the region above a threshold is in cells, as a fraction of the mesh and as the box its centres span. It also reads whether anything was watching the temperature -- a `scalarTransport` field is not one the outer loop solves, so naming it in `residualControl` does nothing, and one heated run here stopped at iteration 87 on p and U with T's residual at 6e-3 -- and differences the two last written T fields beside the Nusselt number they underwrite. Conjugate cases are per region off `constant/regionProperties`, and a case with one region says so. Findings in preflight's measured/means register, `--json`, and `--png` for the per-patch heat rates and the temperature distribution. It edits nothing and exits 0 whatever it finds. |
| `mesh_quality.py` | The cells that failed, rather than the number they failed on. The quality numbers are already in three places -- `mesh_digest.py` tabulates what `checkMesh` printed and applies no thresholds, `preflight.py` applies the conventional ones with a suggested repair, `results.py` draws histograms of whatever quality measures the VTK build will compute -- and all three answer "how bad" and none of them "bad where", which is the half that decides what to do: max skewness 11 in four cells on a trailing edge is a snap artefact, the same 11 in a band across the domain is a mesh to throw away, and the two look identical in every report here. So this is the locator for a mesh metric, built the way `locate.py` is the locator for a diverging field, and reading no mesh file of its own: `locate.read_mesh` loads `constant/polyMesh` ascii or binary, `layer_report.py`'s decompositions do the geometry, `locate.cell_patches` and `locate.bbox_facts` place a cell, and `heat.nearest_patch` answers "near what" for one in the middle. Per failing or marginal metric: how many cells, what fraction of the mesh, the box they span as a fraction of the domain, the patches they sit on, the worst few with coordinates and distance to the boundary, and **a PNG of them inside the mesh** -- the whole domain with the bad cells red, beside a close-up where their neighbours give the reader the local cell size to judge a sliver against. The faces are built from the polyMesh rather than read back through `pyvista.OpenFOAMReader`, whose polyhedron decomposition renumbers cells, since a red cell at the wrong index is a picture that lies. Two routes get the cells and which one drew is printed in the report, in the JSON and on the image: a `cellSet`/`faceSet` that `checkMesh -writeSets vtk` left under `polyMesh/sets`, read by whatever name is on disk rather than by a hardcoded list; or skewness and non-orthogonality recomputed here by `primitiveMeshTools`' own formulae, which VTK's `skew` and `aspect_ratio` are not and so cannot be compared with a `checkMesh` threshold. Aspect ratio is read and never recomputed, for that reason. Second half is **mesh conversion**, probed with `shutil.which` the way `cfmesh.py`'s `where` probes for its meshers and reported in both directions with what is missing named: Fluent, gmsh, VTK, I-DEAS unv, cfx4 and STAR-CCM have converters in the distribution, CGNS has none in either direction and that is a fact about OpenFOAM rather than about this image. A clean mesh says so, a missing converter is reported by the binary it looked for, `--json` carries the same facts, and it exits 0 whatever it finds. |
| `cfmesh.py` | The other mesher on this image, and the four traps between you and it. snappyHexMesh's layer stage is a loop that inserts prisms and then deletes them where a quality metric fails -- on one hull it reached 88.6% coverage on its first iteration and eroded to 66.7% by its fiftieth, then printed 66.7% and exited 0; cfMesh's `cartesianMesh` extrudes a sheet and optimises afterwards, so nothing can un-extrude a face, and it covered 100.0% of the same wall. It is prebuilt in the image, needs no build, no volume and no exports, and was available and unused for four rounds. `where` says whether that is still true of the image you are on: it probes eight binaries -- the four meshers, `generateBoundaryLayers`, and three more it runs itself (`surfaceFeatureEdges` and `surfaceToFMS`, which the record files under surface prep, and `improveSymmetryPlanes`, which it files under mesh tools) -- and names the three boundary-layer classes that never were executables, so a session does not conclude the install is broken. (The image ships 25 in all; the other seventeen are listed in `qa-runs/comp/cfmesh/README.md` and this does not go looking for them -- including `surfaceGenerateBoundingBox`, which is left out on purpose because it is trap 2 and `box` replaces it.) `box` writes a body and its domain box as one closed multi-solid STL, refusing a body that pokes through the box and naming the faces it merely touches, because those are cut planes. `case` writes a `meshDict` whose keys and whose `surfaceFile` decide each other: `surfaceFeatureEdges` indexes every solid name, so against the `.ftr` it writes the key must be the regex `"hull_.*"` and a literal matches nothing -- warned once on the mesh side and *nothing at all* on the surface side, then meshed with no refinement and no layers at exit 0 -- while against a raw STL the solid names arrive verbatim and the literal is the right key, which is how cfMesh's own tutorials are written. It refuses the requests cfMesh accepts and quietly drops (one layer on a patch, a thickness ratio under 1, and type `symmetryPlane` wherever a type can be asked for -- `--patch NAME:TYPE`, `--default-type`, and `meshdict()`'s `wall_type`; `--wall` takes a name and not a type). It also says what `renameBoundary` merges: a `defaultName` that is present makes cfMesh fold every unnamed solid into ONE patch -- added only where a solid is in fact left over, so naming all of them leaves no `farField` at all -- and `--wall hull` alone gives a two-patch mesh with all six box faces in `farField` and no inlet to name -- `--patch xMin:patch` and `--symmetry yMin` are how faces are kept apart. `prepare` is the two edits that make an existing snappy mesh readable, in the order that works. `check` reads back what the mesh got: whether the wall kept its name, whether the wall's own face size is nearer the `cellSize` the `localRefinement` key that names THIS wall asked for or the floor it falls back to without it (`boundaryCellSize` where the dictionary sets one, `maxCellSize` otherwise) -- and where no key names the wall, or the two sizes are less than one octree halving apart, it says it cannot tell rather than guessing, and the coverage number from `layer_report.py`. What it cannot do is printed where the choice is made: cfMesh sizes the layer stack from the local cell, so there is no y+ to ask for, only one to measure afterwards. |
| `gallery.py` | The manifest turned into a self-contained `gallery.html`, a contact sheet, and a list of the latest artifact of each kind. Images are embedded, so the page is the same page on a laptop that has never seen `/work`. |
| `first_look.py` | A meshed but unrun case as one contact sheet: geometry, the whole mesh, a close-up on whatever it was refined around, the named patches, and the counts. Panels that fail print their error in place rather than taking the sheet down, and one `read_file` on the result is the state of the case before a core-hour is spent. |
| `progress_report.py` | Phase, the time reached, the pace, and the exact paths of the pictures that already exist — one answer to "what is happening?" assembled from the case rather than from a log tail. Ladder rung outcomes recorded on the volume surface here too, so a fresh session sees what an earlier one established. |
| `report.py` | The whole study as one PDF, when a document is what is wanted: a cover with the study's identity, the key numbers and one hero figure; the figures grouped the way `gallery.py` groups them, a deleted one still on the page as MISSING; a methods section read out of `controlDict`, `fvSchemes`, `fvSolution`, the transport and turbulence dictionaries, `0/`, `checkMesh` and the solver log; and what the study itself recorded as skipped or failed. The writer is matplotlib's `PdfPages`, since the instance has no PDF library and no network to get one. The cover's numbers are not simply printed next to the picture: each is matched against the claim stamped in a figure's own bytes (`claims.py`), so it comes out `verified` with the figure named, `disagrees` with both numbers and the gap, or `unverified` -- which is what a coefficient nobody drew is. `--hero` overrides the chosen figure and the rule that chose it is printed either way; `--template` takes a JSON cover/section file (`report_template.json` is an example) and a `--template` that is not there is refused rather than quietly replaced by the default; `--logo` goes on the cover; `--json` lists what went in and what was missing. `results.md` stays the working record -- this is the thing you can hand to somebody. |
| `results.py` | A finished case as the standard set of pictures and plots in one call, rather than a render command per view. |
| `probe.py` | Any solved field sampled where it is asked for, as JSON on stdout (and `--out`): `--fields` lists what the case wrote with kind, units and range; `--line` and `--points` interpolate it (a vector as signed components and magnitude, a point off the mesh as `null`); `--region` gives a volume-weighted mean, min, max or integral over an x-y box; `--section-mean --at-x X [--weighted flux]` and `--between X0 X1` give area- or flux-weighted section means and their difference; `--flux --at-x X` the volumetric flux; `--streamlines --seeds` the polylines from each seed. `p_total` is derived when the case did not write it. `--png` draws a line or the streamlines. Reads through `render.py`'s reader, so any physics and any field names; a candidate directory with one case under it is read through it. |
| `balance.py` | Where the flow goes inside a duct and what it costs, which `probe.py` could measure at a section and never across a boundary: every patch the mesh declares, with its area, its signed flux, its area-averaged and its flux-weighted (mixed-mean) pressure, and the share of the total inflow or outflow it carries -- so a manifold's three outlets come out 14/33/52 instead of as one number per section. Inflow and outflow are told apart by the sign of U . A and never by a patch's name, a name being somebody else's convention and a sign a measurement: a patch called `outlet` that this case runs backwards through comes out as the inlet it is. The mass-balance closure sits beside the split -- total in minus total out, absolutely and against the throughflow, stated rather than judged, since what counts as closed is the solver's own continuity tolerance -- with the patches that were counted listed by name, a case that does not close usually having one nobody told the analysis about. The pressure drop between two patches or two x-sections (the sections through `probe.py`'s own flux-weighted section mean, which is the honest average for a duct) is reported as static **and** total, because quoting one as the other is the classic duct error and the gap between them is the velocity head. Then the two dimensionless numbers nothing here had: the loss coefficient K = dp_total/(0.5 rho U_ref^2), which `ladder.py`'s one-geometric-feature rung reads against Borda-Carnot's (1 - A1/A2)^2 and the handbook tables, and the Darcy friction factor f = dp/((L/D) 0.5 rho U^2) off the static drop. rho, U_ref, L and D are refused by name rather than defaulted, on `grade.py:_need`'s rule, a K off a reference velocity taken at the wrong section being out by a factor and looking exactly as measured as a right one. Which pressure convention the case wrote is read off `p`'s own `dimensions` -- kinematic m^2 s^-2 or absolute Pa -- and printed with every number, rho cancelling in K and not in a dp asked for in pascals. `--json` for a script to read, `--png` for the split as a bar chart with the drop under it; the exit code is 0 whatever the balance says, a refusal being a missing constant rather than a finding. |

| `spectra.py` | How fast a force history oscillates and whether it has stopped moving yet -- the two questions a transient run raises and nothing here could answer. There was no FFT anywhere in the package: the only frequency ever measured was a zero-crossing count inside `benchmarks/moving_mesh/grade.py`, which is offline grading code a study cannot reach, needs whole cycles about zero, and reports nothing at all below two crossings -- so studies quoted a Strouhal number from a paper instead of measuring one. This is Welch's spectrum on `numpy.fft` alone (scipy is not on the image), each segment linearly detrended before it is Hann windowed, because a Cd still settling carries a ramp whose power lands in the same low bins a slow shedding tone does and outbids it. The number beside the peak is its prominence -- peak over the spectrum's median -- since a single periodogram of white noise has a tallest bin some nine times its own median and `argmax` alone therefore always finds a "frequency"; a flat spectrum comes back `aperiodic` with that number attached. The verdict is `periodic`/`aperiodic`/`too-short`, the last from how many cycles of the frequency found the record actually spans, because one cycle fits a sinusoid, a ramp and a step equally well. St = f L / U appears only with both `--length` and `--speed`: no diameter is read off the mesh and no free-stream speed off anything, which is `grade.py:_need`'s rule. Settling is what makes `results.py`'s tail mean mean something -- the earliest sample from which the halves' means agree inside the halves' own scatter, and a mean over that window with a 95% interval on the EFFECTIVE sample size, the count divided by the integral time scale of its own autocorrelation, since a history written every time step has consecutive rows agreeing to three figures and 20,000 correlated samples are not 20,000 measurements. Every judgement is printed next to the number it came from. What the detrend cannot remove is a curve: a settling transient is an exponential, its power lands in the same low bins, and a `1.2 + 3 exp(-t/2)` Cd reported its tallest bin at 0.084 Hz -- the transient, not the flow -- which is what `--from` is for, the settling section having just said where that transient ends. Anything that writes a PNG is worth knowing about twice over, because `read_file` on an
image path hands the picture back to you rather than its bytes — so a render is
something you can look at, not only something you can produce.

`ENVIRONMENT.md` lists what is installed on this instance — the Python packages, the
binaries on PATH, and which tool does a job (PDF is `pdftoppm`, not `fitz`; gifs are
`imageio`; meshing is `gmsh`) — so the environment can be read rather than probed, and the
sealed network is stated once rather than met as a surprise.

`templates/` holds the gmsh recipes as working scripts rather than as prose
to retype: `duct2d.py` for a plane case, `body_in_box.py` for a body in a flow box, and
`free_surface.py` for a two-phase dam break -- the one of the three that writes a case
meant to be solved rather than only meshed,
each copy-edit-run, each ending in `checkMesh` and a `mesh_look.py` call. They are kept
for whoever is working in bash. The CAD desk no longer copies and edits them — it works
a cell at a time in a kernel, and `templates/prep/` and `templates/snappy/` are the
pages it reads instead — but a recipe that runs is still the fastest way for a person,
or for the main agent, to get a plane case or a body in a box meshed without one.

`notes/openfoam-field-notes.md` is OpenFOAM practice written as field notes rather than
procedure. `notes/free-surface-field-notes.md` is the same for two-phase VOF work, where
most of the ways a case is wrong leave a run that finishes and logs nothing: the
interface Courant limit, `p_rgh` against `p`, an open boundary that has to let flow back
in, why a uniform `alpha` start is not an initial condition, and how a smeared interface
and a resolved one differ in a picture. `notes/bundle-layout.md` is one suggested `/work` layout, labelled a
suggestion. `notes/openfoam-agent-architecture.md` is a longer design document, optional
reading.
